# ADR-0026: 経歴書ドラフトのプロジェクト明細化と候補選択制への縮小

## コンテキスト

ADR-0018 → 0020 → 0025 で「GitHub 連携データから経歴書ドラフトを生成し、フォームへ流し込む」導線は完成した。しかし運用してみると、**生成物がそのまま経歴書として使えない**。原因は 3 つあり、いずれも実装に現れている。

### 1. 経歴書の核心部分を機械がプレースホルダで埋めている

GitHub には職歴情報（会社・案件・役割・工程・チーム規模）が存在しない。にもかかわらず `mapper.py` は Resume 互換の構造を満たすために固定値を生成している。

| 経歴書の項目 | 現在の生成値 | 出典 |
|---|---|---|
| 会社名 | `"個人開発"` 固定 | `mapper.py` `PLACEHOLDER_COMPANY` |
| 事業内容 | `"GitHub 上での個人開発活動"` 固定 | `mapper.py` `PLACEHOLDER_BUSINESS_DESCRIPTION` |
| 役割 | `"開発（個人開発）"` 固定 | `mapper.py` `PLACEHOLDER_ROLE` |
| チーム構成 | 常に 1 人（`{"total": "1"}`） | `mapper.py` `_build_project` |
| 顧客名 | 常に空 | `mapper.py` `build_skeleton` |
| 担当工程 | 常に空 | `mapper.py` `_build_project` |

さらに `build_skeleton` が返す experiences は**常に 1 件**で、「3 社 5 案件」のような実務経歴の構造は原理的に出せない。ADR-0018 は「捏造につながる値（担当工程・チーム規模の水増し等）はここでは生成しない」と明記しているが、**構造を満たすための固定値生成は残っており**、結果として「経歴書の体裁だが中身が無い」ものが出る。

### 2. 注入が既存の実務経歴を破壊しうる

`web/src/utils/resumeImport.ts` の `applyResumeDraftToForm` は、experiences に中身があれば**丸ごと置換**する。ADR-0025 が不変条件として掲げた「反映でユーザーの既存データを不用意に消さない」は、スカラー（preserve-if-empty）には効いているが**配列には効いていない**。実務経歴を書き終えたユーザーが上書き確認を承認すると、3 社分の経歴が「個人開発」1 件に置き換わる。

### 3. 選定順がノイズを最大化している

`mapper.py` の `select_repos` は第 1 キーが**最終 push 日時の降順**、第 2 キーが言語バイト合計。この並びでは「昨日 README を直しただけのチュートリアル」が「半年前に作り込んで完成させた本命」に勝つ。チュートリアル・todo アプリ・写経リポジトリが上位 5 件を占めうる。

原因は選定ロジックの甘さというより、**判別材料がドラフトに届いていない**ことにある。収集層の `RepoData`（`github_collector.py`）は topics / stargazers_count / package_declarations / infra_declarations / imported_symbols まで保持しているのに、キャッシュへ永続化される `AnalyzedRepoSummary`（`schemas/github_link.py`）は **full_name / description / created_at / pushed_at の 4 フィールドだけ**。mapper は最終 push 日時と言語バイト数しか使えない。

なお既存の `_passes_filter`（`github_collector.py`）は private / fork / サイズ下限 / N 年以内という**入口の足切り**のみで、「経歴書に載せる価値があるか」は評価していない（連携ダッシュボードの集計用フィルタなので、これ自体は正しい）。

## 決定内容

**ドラフトの生成単位を experience から project（プロジェクト明細）へ落とし、リポジトリの採否を機械の自動選定から人間の選択へ移す。** ADR-0018 のハイブリッド方式（構造 = ルールベース / 自然文 = LLM）、ADR-0020 の非同期タスク構造・課金の原子性、ADR-0010 の DB 非更新原則は変えない。

### 1. 出力単位を project にし、プレースホルダ生成を廃止する

- ドラフトが返すのは**プロジェクト明細のリスト**とする。experience（会社・事業内容・在籍期間・顧客）は**生成しない**。
- `PLACEHOLDER_COMPANY` / `PLACEHOLDER_BUSINESS_DESCRIPTION` / `PLACEHOLDER_ROLE` / チーム構成の固定値生成を**削除**する。GitHub から得られない値は機械が埋めず、空のまま人間が書く（ADR-0018 の「捏造につながる値は生成しない」の徹底）。
- project が持つ値は以下に限定する。`role` / `phases` / `team` は空で返し、人間が埋める。

| フィールド | 生成方式 |
|---|---|
| `name` | ルールベース（リポジトリ名） |
| `periods` | ルールベース（`created_at` 〜 `pushed_at`） |
| `technology_stacks` | ルールベース（ADR-0016 のスキル証跡） |
| `description` | LLM（採用されたプロジェクトのみ） |
| `role` / `phases` / `team` | **生成しない**（空 = 人間が埋める） |

- `career_summary` / `self_pr` は引き続き LLM が生成するが、experiences とは独立した**候補**として返す（決定 5）。

### 2. リポジトリの採否は人間が決める（候補提示 + 選択）

- 機械が上位 5 件を確定させる現行方式を廃止し、**シグナル付きの候補一覧**を提示してユーザーがチェックで採用する。
- **機械は候補を落とさない**。ノイズ判定は「候補一覧からの除外」ではなく**デフォルト非選択 + 理由の表示**で表現し、ユーザーが常に覆せるようにする。「経歴書に載せる価値があるか」は本人にしか判断できない（社内向けの地味なツールが最も効く、といった事例を機械が閾値で落とすリスクを避ける）。
- LLM による説明文生成は**採用されたプロジェクトに対してのみ**実行する。現行は常に最大 5 件分を生成しており、選択数に比例するコストへ改善される（P1）。
- `PROJECT_LIMIT = 5` の意味を「LLM 出力の有界化」から「1 回の生成で選べる上限」へ変える（値は据え置き）。

### 3. 並び順とデフォルト選択のヒューリスティック

- **主キーを「継続期間 × 実装量」に変更する**。継続期間は `pushed_at − created_at` で算出する。チュートリアル・写経は数日で終わり、実プロジェクトは数ヶ月〜数年継続するため、単一シグナルとしての判別力が最も高い。直近性（`pushed_at`）は**タイブレークへ降格**する。
- デフォルト非選択にする条件（理由バッジを併記する）:
  - 継続期間が閾値未満
  - topics に学習用途を示す語（`tutorial` / `practice` / `sample` / `study` / `learning` / `handson` 等）を含む
- **stars は選定に使わない**。個人開発では本命リポジトリでも 0〜1 が普通で、判別力が無い。
- **順序は完全順序とし、同点でも並びが一意に決まることを保証する**。最終 tie-breaker は `full_name` の辞書順とする（現行 `select_repos` が持つ決定論保証をそのまま引き継ぐ）。同一入力から常に同一の並びが出ることを不変条件として維持する。
- **スコアの具体式・継続期間の閾値・topics の正規化規則は ADR では固定しない**。本 ADR が決めるのは「主キーは継続期間と実装量」「直近性はタイブレークへ降格」「最終 tie-breaker は `full_name`」「stars は使わない」までとする。実際の重み・閾値・語彙は調整対象であり、正本は `resume_draft/mapper.py` の定数に置く（ADR に数値を複製すると drift する。#562 で定義しテストで固定する）。
- 選定ロジックは決定論的な純関数として維持し、`[tool.mutmut]` の `only_mutate` に加えてミューテーションテスト対象にする（ADR-0017 / 0019。判定ロジックが増えるため、テストの検出力を計測対象に含める）。

### 4. 選定シグナルをキャッシュへ永続化する（`AnalyzedRepoSummary` の拡張）

- `AnalyzedRepoSummary` に topics / 言語バイト合計 / 依存の厚み（direct 宣言数・エコシステム数）/ IaC 宣言の有無を**後方互換の Optional フィールド**として追加する（ADR-0018 決定 4 と同じパターン）。
- **GitHub API の追加取得はしない**。すべて連携実行時に `RepoData` が既に保持している値であり、収集層から永続化層へ渡す経路を通すだけで足りる。
- 旧形式キャッシュ（当該キーが無い）のユーザーには、ADR-0018 が定めた既存契約どおり 409 を返して再連携を促す。

### 5. 注入は「置換」ではなく「追加」にする

- `applyResumeDraftToForm` の experiences 丸ごと置換を**廃止**する。
- 採用したプロジェクトは、ユーザーが指定した**既存 experience の `clients[].projects` へ追加**する。既存の experience・client は書き換えない。
- **追加先はユーザーの明示指定を必須とする**（experience と client を選ばせる）。機械が推測して追加先を決めない。
- **注入は冪等とする**。同一 client 内に**同名の project が既に存在する場合は追加しない**。project name はリポジトリ名（`full_name` の末尾）であり、同じドラフトを 2 回適用しても project が増殖しない。
  - 判定キーに project name を使い、**由来リポジトリを保持する専用フィールドは新設しない**。`full_name` を安定 ID として持たせる方が堅牢だが、`ResumeProject` は DB 永続化される保存契約であり、スキーマ変更・マイグレーション・codegen まで波及した上、手入力の project には常に空の列が増える。異なる owner の同名リポジトリだけが衝突するが、1 ユーザーの経歴書内で起きる確率は低く、起きても重複追加が抑止されるだけで既存データは壊れない。
- **追加先の experience / client が 1 件も無い場合**は、空の experience と client を 1 件ずつ作ってそこへ追加する（会社名・事業内容は空のまま人間が埋める。決定 1 のプレースホルダ廃止と整合させる）。
- **注入は部分適用しない**。追加処理が途中で失敗した場合はフォーム state を変更前のまま維持する（ADR-0010 の DB 非更新原則と同様、確定前の状態を壊さない）。
- `career_summary` / `self_pr` は上書きせず、`AgentChatWidget` と同じ「候補提示 → ユーザーが適用」の経路に統一する。
- これにより ADR-0025 のマージ規則（preserve-if-empty）が配列にも実質的に効き、「反映でユーザーの既存データを消さない」が全フィールドで成立する。

## 代替案

- **機能を全量撤去する（ADR-0022 の流儀）**: プレースホルダ問題・選定問題を根本から消せる。しかし (1) 技術スタックの証跡（ADR-0016 の 3 層スキル検出）は GitHub にしか無い情報で、手入力より正確な唯一の供給源である、(2) `resume_draft` は `TaskType` の 2 本目であり、「非同期タスク基盤 × LLM ハイブリッド × 課金の原子性」を実証する唯一の縦串サンプルである（撤去すると `GITHUB_LINK` 1 本に戻り、タスク基盤が汎用化されている実証が失われる）。不採用。ただし縮小後も候補が採用されないなら、ADR-0022 の流儀で全量撤去する（「将来の移行条件」）。
- **現状維持 + 選定ロジックだけ改善する**: ノイズは減るが、プレースホルダ生成と experiences 置換は残る。「そのまま使えない経歴書が出る」という本質的な問題が解決しない。不採用。
- **機械が閾値でノイズを候補から除外する**: 実装は単純だが、価値判断を機械が代行して本命を落とすリスクがある。デフォルト非選択 + 理由表示で代替する。不採用。
- **stars / fork 数でランキングする**: 一般的な OSS 評価指標だが、個人開発リポジトリでは本命でも 0 が普通で判別力が無い。不採用。
- **「経歴書に載せる価値があるか」を LLM に判定させる**: 決定論で扱える選定を LLM に投げる理由がなく（P5）、判定根拠をユーザーに説明できない。トークンコストも候補数に比例して増える。不採用。
- **README を取得して説明文の品質を上げる**: ADR-0018 が既に「トークンコストと連携時間の増加に見合わない」として見送った判断。本 ADR の論点（何を生成するか）とは別軸のため、ここでは再評価しない。

## トレードオフ・既知のリスク

- **ワンクリック生成から選択操作へ手数が増える**。ただし現行の生成物はそのまま使えず手直しが必須のため、経歴書完成までの実質的な手数は減ると見込む。
- **継続期間ヒューリスティックは誤判定する**（1 日で作り込んだ価値あるリポジトリ、惰性で更新が続くチュートリアル）。影響範囲をデフォルト選択状態と並び順だけに閉じ込めてあるため、ユーザーが覆せば実害は無い。
- **旧形式キャッシュのユーザーは再連携が 1 回必要**（ADR-0018 の拡張時と同じ。409 + 再連携導線で吸収する）。
- **冪等性の判定を project name に頼る**（決定 5）。異なる owner の同名リポジトリ（例: `alice/todo` と `bob/todo`）を同じ client に入れようとすると 2 件目が追加されない。専用の安定 ID を保存契約へ足すコストの方が大きいと判断して受け入れる。ユーザーは project 名を変えれば追加できる。
- **`career_summary` / `self_pr` の適用経路が Agent チャットと二重に見える**。当面は候補提示として併存させるが、重複が問題になれば Agent 側へ寄せる。
- **ドラフトの魅力が下がる可能性**: 「経歴書が自動で出来上がる」から「プロジェクト候補が出てくる」へ期待値が下がる。これは誇大な期待を正しい水準へ戻す変更であり、意図した効果と判断する。

## 将来の移行条件

- **縮小後も候補が採用されない場合**（候補は出るが選ばれない）は、ADR-0022 の流儀で機能を全量撤去する。撤去対象は `resume_draft` 関連の 4 エンドポイント・`resume_draft_cache` テーブル・`TaskType.RESUME_DRAFT`・dashboard UI・web の注入経路。
- **実務経歴（会社・案件・役割）の供給源を別に得られるようになった場合**は、experience 単位の生成再導入を本 ADR の改訂として検討する。
- **GitHub 以外（GitLab 等）を供給源に追加する場合**は、ADR-0016 のスキル証跡と合わせて選定シグナルを再評価する。
- 選定ヒューリスティックの誤判定が実運用で問題になった場合は、シグナルの追加（コミット数・コントリビューター数）を検討する。ただし GitHub API の追加呼び出しを伴うため、ADR-0018 決定 4 の「連携時に取れるものだけを使う」方針との整合を先に評価する。

## 設計原則との関係

- **P4（責務を層で分離する）**: 中心的な判断軸。ADR-0016 の「機械 = 幅 / 人間 = 深さ」を**選定と採否**にまで延長する。機械は候補の幅と決定論的な構造を出し、価値判断と深さ（役割・工程・チーム）は人間が埋める。
- **P5（デフォルトは決定論、LLM は対話型に限定する）**: 選定・並び順・構造は決定論的な純関数のまま。LLM は人間が採用したプロジェクトの自然文だけを書く。LLM の担当範囲が縮む方向の変更。
- **P6（可逆性を設計する）**: 撤去ではなく生成範囲の縮小を選び、撤退条件（採用されなければ全量撤去）を明記した。生成する値を減らす方向のため、撤退時の削除対象も小さくなる。
- **P1（コスト最適化を第一制約にする）**: LLM 呼び出しが採用件数に比例し、常に最大 5 件を生成する現行より安くなる。GitHub API の追加呼び出しはしない。

### 実装で確定した事項（ADR では固定しなかったもの）

決定 3 で「ADR では固定しない」とした値の**正本は `backend/app/services/agent/resume_draft/mapper.py` の定数**。
数値をここへ複製すると drift するため、参照先だけを記す。

| 事項 | 正本 |
|---|---|
| 選定スコアの式（継続期間 × 実装量。整数演算のみ） | `mapper.selection_score` |
| 実装量に含めるフィールドと重み | `mapper.implementation_volume` / `*_VOLUME_WEIGHT` |
| 継続期間の閾値（デフォルト非選択の境界） | `mapper.MIN_DURATION_DAYS` |
